## 🧠 메모리 관리 — 논문

**AgeMem (2601.01885) — 메모리 연산을 "툴 액션"으로 통합.** 지금까지 장기(LTM)·단기(STM) 메모리를 별도 컴포넌트+휴리스틱으로 다뤘다면, AgeMem은 **메모리 조작(저장·검색·갱신·요약·폐기)을 에이전트 정책 안의 툴 호출로 노출** — 모델이 매 스텝 일반 텍스트 토큰 또는 메모리 툴 콜을 자율 선택.
- 학습은 **3단계 점진 강화학습 + step-wise GRPO**로 희소·불연속 보상 문제 완화. 5개 롱호라이즌 벤치마크에서 메모리 증강 베이스라인 대비 성능·메모리 품질·컨텍스트 효율 모두 개선.
- 🔗 [Agentic Memory / AgeMem (arXiv)](https://arxiv.org/abs/2601.01885) · [해설 (MarkTechPost)](https://www.marktechpost.com/2026/01/12/how-this-agentic-memory-research-unifies-long-term-and-short-term-memory-for-llm-agents/) · [메모리 서베이 (arXiv 2603.07670)](https://arxiv.org/abs/2603.07670)
- 🧠 **Claude가 배울 것:** 내 메모리 쓰기를 "수동 규칙"이 아니라 **저장·갱신·폐기를 스스로 판단하는 툴 액션**으로 보는 관점 — 어제 A-MAC(쓰기 게이팅)와 한 쌍. 정제(Reflection) 정책을 툴화하면 멱등·자율 관리에 유리.
- 👤 **내가 알 것:** 우리 `memory/` 파일+MEMORY.md 인덱스 방식은 이미 "툴 기반 외부 스토어"에 가까움. 다음은 **무엇을 버릴지(discard) 자동 판단** 추가 — 안 쓰는 메모 정리 정책 초안 검토.

## 📓 Obsidian / PKM / 로컬 LLM

**2026년 PKM은 3-아키텍처로 수렴.** Karpathy식 LLM Wiki 패턴이 계속 확산되는 가운데, 실무 셋업이 규모별 셋으로 정리됨 — **① Obsidian-centric**(노트 우선, ~5만 아이템) **② AnythingLLM-centric**(문서 우선, ~10만) **③ Python+ChromaDB**(엔지니어 우선, 100만+).
- 핵심은 동일: raw/ 디렉터리에 원문 수집 → LLM이 점진적으로 구조화 마크다운 위키로 컴파일 → Obsidian이 가벼운 프런트엔드. Ollama 조합이면 완전 로컬·오프라인, 관리 오버헤드 30~40% → 10% 미만.
- 🔗 [로컬 LLM 지식베이스 구축 가이드 (modemguides)](https://www.modemguides.com/blogs/ai-infrastructure/local-llm-knowledge-base-obsidian-setup-guide) · [Karpathy LLM Wiki + Claude Code 셋업 (Alfonso Fortunato)](https://alfonsofortunato.com/blog/obsidian-pkm-llm-wiki/) · [Obsidian+AI 마스터링 (Eric Ma)](https://ericmjl.github.io/blog/2026/3/6/mastering-personal-knowledge-management-with-obsidian-and-ai/)
- 🧠 **Claude가 배울 것:** 우리 llm-wiki는 **①Obsidian-centric**(~5만 규모)에 정확히 해당 — index.md 라우팅 → 개념페이지 → 원문 3-read를 유지하면 이 규모에서 충분. 100만+ 가면 ChromaDB 검토.
- 👤 **내가 알 것:** 지금 vault가 커지면 어느 아키텍처로 넘어갈지 기준이 생김. 당분간은 Obsidian-centric로 충분, 로컬 검색(Ollama) 결합만 옵션으로.
